📈 Lock granularity and escalation

SQL Server

Locks form a hierarchy. Before taking a row lock, SQL Server takes intent locks (IS / IX) on the page and table, so a later table lock request can see the conflict without scanning every row lock.

DATABASE→OBJECT (table)→HoBT / partition→PAGE→KEY / RID (row)

Escalation goes from row or page locks straight to the table (or partition with LOCK_ESCALATION = AUTO). It never escalates row → page.

  • Trigger: one statement holds about 5,000 locks on a single table or index (row + page locks on that object), or lock memory crosses the engine's memory threshold.
  • If escalation can't get the table lock because of another session's conflicting lock, the statement keeps its row/page locks and tries again after every 1,250 additional locks.
  • Fixes: batch DML in chunks under ~4,000 rows, add an index so fewer rows are touched, LOCK_ESCALATION = AUTO on partitioned tables. DISABLE (or trace flags 1211/1224) trades blocking for lock memory; use with care.
  • Optimized locking (Azure SQL Database and SQL Server 2025, needs ADR) holds one TID lock per modified row only until the row is updated, which mostly removes escalation. Not available on SQL Server 2019/2022, including RDS.
RDS SQL Server: there is no startup-parameter access; global trace flags are set through the DB parameter group, and only the flags AWS lists for your engine version are allowed (check whether 1211/1224 are among them). Prefer per-table ALTER TABLE … SET (LOCK_ESCALATION = …) and batching. See escalation counts per index with sys.dm_db_index_operational_stats (query in the Diagnostics section).
PostgreSQL

PostgreSQL never escalates. Row locks are written into the row itself, so locking a million rows costs no lock memory. What uses the shared lock table is one entry per relation (table, index, partition) per transaction, plus advisory and other object locks.

  • Shared lock table size ≈ max_locks_per_transaction × (max_connections + max_prepared_transactions). One transaction may use more than 64 as long as the total fits. When it runs out: ERROR: out of shared memory · HINT: You might need to increase max_locks_per_transaction.
  • Common triggers: pg_dump of thousands of tables, queries over heavily partitioned tables without pruning, a big DROP SCHEMA … CASCADE.
  • Fast-path: each backend keeps its first 16 weak locks (AccessShare / RowShare / RowExclusive) outside the shared table (PG ≤ 17; PG 18 sizes it from max_locks_per_transaction). Beyond that, heavy partition use shows up as LWLock:LockManager waits.
  • Advisory locks are app-defined: pg_advisory_lock(key) (session, must unlock), pg_advisory_xact_lock(key) (released at commit), pg_try_advisory_lock(key) (no wait, returns boolean). They appear in pg_locks with locktype = 'advisory'.
Aurora PostgreSQL: max_locks_per_transaction is static, so changing it in the cluster/DB parameter group needs a reboot. In Performance Insights, lock waits appear as Lock:relation, Lock:tuple, Lock:transactionid, Lock:advisory; lock-manager contention as LWLock:lock_manager / LWLock:LockManager.
